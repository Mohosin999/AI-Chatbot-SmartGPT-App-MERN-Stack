## Overview

When a user sends a message, this is the high-level flow:

```
Frontend (SSE request)
  → streamCreate controller (validation, SSE setup)
    → streamMessage (core pipeline)
      → Load chat from MongoDB
      → Save user message to chat
      → Split messages: recent 10 vs older
      → Summarize older messages via AI
      → Build contents array (system + summary + recent + current)
      → Handle files (images as inlineData, PDFs as extracted text)
      → Stream response from Gemini
      → Save AI reply to MongoDB
      → Return chunks via SSE
```

## Entry Point

**File:** `src/api/v1/message/controllers/streamCreate.ts`

```typescript
// Line 10: Extract userId from authenticated request (set by middleware)
const userId = req.user!.id;

// Line 12-20: Validate request body with Zod schema
const parsed = createMessageSchema.safeParse(req.body);

// Line 24-25: Create AbortController — if client disconnects, we abort the AI call
const abortController = new AbortController();
const signal = abortController.signal;

// Line 27-29: Listen for client disconnect → abort AI generation
req.on("close", () => {
  abortController.abort();
});

// Line 31-34: Set SSE headers — tells browser this is a streaming response
res.setHeader("Content-Type", "text/event-stream");
res.setHeader("Cache-Control", "no-cache");
res.setHeader("Connection", "keep-alive");
res.setHeader("X-Accel-Buffering", "no"); // Disable nginx buffering

// Line 37-45: Call the core pipeline
const { stream, complete } = await streamMessage({
  userId, chatId, prompt, files, signal, schema, tools,
});

// Line 47-50: Stream each chunk as SSE event
for await (const chunk of stream) {
  res.write(`data: ${JSON.stringify({ chunk })}\n\n`);
}

// Line 52: After streaming ends, save the full reply to MongoDB
const reply = await complete();

// Line 54-57: Send final "done" event with the complete message object
res.write(`data: ${JSON.stringify({ done: true, message: reply })}\n\n`);
```

**Why SSE (Server-Sent Events)?** — The AI response can be long. Streaming lets the user see tokens appear in real-time instead of waiting for the full response.

**Why AbortController?** — If the user navigates away or clicks "Stop", the browser closes the connection, `req.on("close")` fires, and the AI generation is aborted to save tokens/cost.

## Context Building Pipeline

**File:** `src/lib/message/index.ts` — `streamMessage()` function

This is the core of the system. Here's each step:

### Step 1: Load Chat & Save User Message (Lines 72-97)

```typescript
// Line 72-74: Find the chat in MongoDB. Must belong to this user.
const chat = await Chat.findOne({ userId, _id: chatId });
if (!chat) throw notFound();

// Line 76-80: Build user message object
const userMessage: Record<string, unknown> = {
  role: "user",
  content: prompt,
  timestamp: Date.now(),
};

// Line 97: Push to chat's message array (will be saved to MongoDB later in complete())
chat.messages.push(userMessage as any);
```

**Why save BEFORE generating?** — If AI generation fails, the user's message is still recorded. This ensures we don't lose user input.

### Step 2: Auto-Generate Chat Title (Lines 98-106)

```typescript
// Line 99-100: Check if this is the first message in a new chat
const needsTitle = !chat.name || /^(new chat|untitled)/i.test(chat.name.trim());

// Line 104-106: If new chat, fire-and-forget title generation (doesn't block the response)
const titlePromise = needsTitle
  ? generateChatTitle(titleText)
  : Promise.resolve(null);
```

**Why a Promise that's awaited later?** — Title generation is a separate AI call. We don't want to block the main response. We await it in `complete()` after streaming finishes.

### Step 3: Split Messages — Recent 10 vs Older (Lines 108-110)

```typescript
// Line 108: Get all messages except the one we just pushed (the current user message)
const allMessages = chat.messages.slice(0, -1);

// Line 109: Last 10 messages → sent in FULL to AI
const recentMessages = allMessages.slice(-RECENT_MESSAGE_LIMIT);  // RECENT_MESSAGE_LIMIT = 10

// Line 110: Everything before the last 10 → will be summarized
const olderMessages = allMessages.slice(0, -RECENT_MESSAGE_LIMIT);
```

**Why 10?** — Balances context quality against token cost. The last 10 messages give the AI enough recent conversation to understand follow-up questions. Older messages lose relevance.

**Why slice(0, -1)?** — We just pushed the current user message to `chat.messages`. We don't want to include it in "history" — it gets added separately at the end with files/attachments.

### Step 4: Summarize Older Messages (Lines 112-117)

```typescript
let droppedSummary = "";
if (olderMessages.length > 0) {
  droppedSummary = await summarizeConversation(
    olderMessages.map((m) => ({ role: m.role, content: m.content })),
  );
}
```

**`summarizeConversation` (Lines 32-45):**
```typescript
// Line 35-37: Format each message, cap at 500 chars each to avoid huge inputs
const text = messages
  .map((m) => `[${m.role}]: ${m.content.slice(0, 500)}`)
  .join("\n");

// Line 39: Ask AI to summarize in 10-20 lines
const prompt = `Summarize this conversation in 10-20 lines. Cover all key topics,
decisions, user preferences, and important details. Be concise but thorough.\n\n${text}`;

// Line 40-41: Use generateContentText (non-streaming, temperature=0 for consistency)
return await provider.generateContentText(prompt);
```

**Why 500 chars per message?** — To prevent one huge message from blowing up the summary input. We only need enough content to understand what was discussed.

**Why temperature=0?** — Summaries should be deterministic and factual, not creative.

**Why `generateContentText`?** — This is a one-shot AI call (not streamed). It uses `temperature: 0` for consistent summaries. Defined in `gemini-provider.ts:264-268`.

### Step 5: Build System Prompt (Lines 119-126)

```typescript
// Line 119-123: Get user's custom instructions from MongoDB
const userData = await User.findById(userId).select("customInstructions").lean();
const customInstr = userData?.customInstructions?.trim();

// Line 126: Build system prompt with user name and optional custom instructions
const systemPrompt = `You are an AI assistant helping ${chat.userName}.
Be helpful, accurate, and concise.${customInstr ? `\n\n[User Instructions]\n${customInstr}` : ""}`;
```

**Why User model query here?** — Custom instructions are set per-user in Settings. We fetch them fresh each time so changes take effect immediately.

### Step 6: Assemble `contents` Array (Lines 128-147)

```typescript
// Line 128-133: First content block = system context (disguised as "user" role)
const contents = [
  {
    role: "user",
    parts: [{ text: `[System Context]\n${systemPrompt}` }],
  },
];

// Line 132-137: If we have a summary of older messages, add it
if (droppedSummary) {
  contents.push({
    role: "user",
    parts: [{ text: `[Earlier context summary]:\n${droppedSummary}` }],
  });
}

// Line 139-144: Add the recent 10 messages in order
for (const msg of recentMessages) {
  contents.push({
    role: msg.role,
    parts: [{ text: msg.content }],
  });
}
```

**Why `role: "user"` for system prompt?** — Gemini doesn't have a "system" role in the `contents` array. System instructions are sent as the first "user" message. This is Gemini's convention.

**Why `[System Context]:` prefix?** — Explicit labeling helps the AI distinguish instructions from conversation. The `[Earlier context summary]:` prefix does the same for the summary.

**Final `contents` structure sent to Gemini:**
```
[0] user: "[System Context]\nYou are an AI assistant..."
[1] user: "[Earlier context summary]:\nUser asked about X, then..."  (if >10 messages)
[2] user: "message 1"     ─┐
[3] assistant: "reply 1"   │ recent 10
[4] user: "message 2"     │ messages
   ...                     │
[N] assistant: "reply 9"  ─┘
[N+1] user: "current message + files"  ← added in Step 7
```

## File Handling

**File:** `src/lib/message/index.ts` (Lines 149-183)

### Images

```typescript
// Line 170-178: For each image file, add an inlineData part
if (files && files.length > 0) {
  for (const f of files) {
    if (f.mimeType.startsWith("image/")) {
      userParts.push({
        inlineData: { mimeType: f.mimeType, data: f.data },  // base64 data
      });
    }
  }
}
```

**Why `inlineData`?** — Gemini's API accepts images as base64-encoded `inlineData` parts alongside text. The model processes both together — it can "see" the image.

### PDFs

```typescript
// Line 149-162: Extract text from PDF using pdf-parse
if (files && files.length > 0) {
  for (const f of files) {
    if (f.mimeType === "application/pdf") {
      const buf = Buffer.from(f.data, "base64");      // Decode base64 to buffer
      const { text } = await pdf(buf);                  // Extract text with pdf-parse
      pdfTexts += `\n\n[PDF Content - ${f.name}]:\n${text.slice(0, 5000)}`;  // Cap at 5000 chars
    }
  }
}
```

**Why text extraction instead of inlineData?** — Gemini processes images natively, but PDFs are not images. We extract the text content and append it to the prompt. The AI reads the extracted text.

**Why 5000 chars?** — Prevents large PDFs from consuming too much of the context window.

## AI Provider Layer

### Provider Interface

```typescript
// Line 26-41: AIProvider interface — abstraction over any AI backend
export interface AIProvider {
  readonly name: string;
  generateContentStream(contents, signal, options): AsyncGenerator<string>;
```

**Why an interface?** — If you switch from Gemini to OpenAI later, you only create a new `OpenAIProvider` class. Everything else (`streamMessage`, controllers) stays unchanged.

### Gemini Provider

**File:** `src/lib/ai/gemini-provider.ts`

#### Role Mapping (Line 17-21)
```typescript
const mapRole = (role: string): string => {
  if (role === "assistant") return "model";  // Gemini calls it "model", not "assistant"
  if (role === "system") return "user";     // No "system" role in Gemini
  return role;
};
```

#### Contents Mapping (Lines 60-70)
```typescript
private mapContents(contents: GeminiContent[]) {
  return contents.map((c) => ({
    role: mapRole(c.role),
    parts: c.parts.map((p) => {
      if (p.functionCall) return { functionCall: p.functionCall };
      if (p.functionResponse) return { functionResponse: p.functionResponse };
      if (p.inlineData) return { inlineData: p.inlineData };  // Images pass through
      return { text: p.text || "" };
    }),
  }));
}
```

**Why map?** — Our internal `GeminiContent` type is flexible. Gemini's SDK expects a specific format. This mapping converts between them.

#### Model Selection (Lines 26-32)
```typescript
private getModel(config?: GenerationConfig) {
```

**Why `gemini-2.5-flash`?** — Fast, cheap, good for chat. Configurable via `GEMINI_MODEL` env var.

## Streaming Response

**File:** `src/lib/message/index.ts` (Lines 212-232) + `src/lib/ai/gemini-provider.ts` (Lines 76-152)

### How streaming works:

```
streamMessage()
  → provider.generateContentStream(contents, signal, options)
    → GeminiProvider._streamWithTools(contents, signal, ...)
      → model.generateContentStream(request)    ← Gemini SDK streaming
      → for await (chunk of result.stream)      ← yield each text chunk
        → yield text
  → for await (chunk of genStream)              ← back in streamMessage
    → fullText += chunk                         ← accumulate full response
    → yield chunk                               ← yield to controller
  → controller writes each chunk as SSE event
```

**Why double streaming?** — `streamMessage` wraps `GeminiProvider`'s stream to:
1. Accumulate `fullText` (needed to save the complete reply later)
2. Check `signal.aborted` (stop if user clicked "Stop")
3. Handle tool call recursion transparently

## Tool Calling Flow

**File:** `src/lib/ai/gemini-provider.ts` (Lines 110-152)

```
AI receives request with tool definitions
  → AI decides to call a tool (e.g., calculator)
  → Response contains functionCall parts
  → We execute the tool locally via onFunctionCall callback
  → We append: original contents + AI's functionCall + our functionResponse
  → We recurse (up to depth 5) with the updated contents
  → AI sees the tool result and generates final text response
```

```typescript
// Line 84-87: Safety limit — prevent infinite tool loops
if (depth > 5) {
  yield "I've used too many tools to answer this.";
  return;
}

// Line 115-125: Execute each function call the AI requested
for (const fc of functionCalls) {
  const toolCall: ToolCall = {
    name: fc.name,
    args: JSON.stringify(fc.args ?? {}),
    id: fc.name,
  };
  const result = await onFunctionCall(toolCall);  // Runs the tool
  toolResults.push(result);
}

// Line 134-138: Append tool results to conversation, then recurse
const updatedContents = [
  ...contents,
  { role: "model", parts: functionCallParts },    // What AI wanted to call
  { role: "user", parts: functionResponseParts },  // Our tool's response
];

// Line 141-151: Recurse — AI sees results, generates final answer
for await (const chunk of this._streamWithTools(updatedContents, ...)) {
  yield chunk;
}
```

**Why recursion?** — A single AI turn might need multiple tool calls. Each round, the AI sees previous results and decides if it needs more tools. Max 5 rounds prevents runaway loops.
